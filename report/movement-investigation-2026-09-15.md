# 400 人沙盒交战性能调查与优化方案

2026-09-15。调查对象为盾卫、火枪手等步兵的大规模沙盒交战。证据包括用户提供的三张分析器截图、当前项目源码、Godot 4.6.3 官方源码、10 次有画面的隔离运行，以及两个移动优化原型的行为测试。

**后续 GPU 核对补充：截图右半区确有 GPU 历史尖峰超过 16.67 ms。本文引用的 6.42 ms 仅属于当前选中帧，不能据此排除 GPU 瞬时超预算。** 图表含义、分辨率对照及硬件遥测见 [GPU 专项调查](gpu-investigation-2026-09-15.md)。

## 结论

**本轮首先确认了分析器对测量结果的明显扰动；尚未复现截图中的同一阵型，也没有证明原生碰撞是持续交战的主要瓶颈。** 固定的 400 人沙盒样本在 Release 下持续阶段为 102.95／103.90 FPS；同源码的调试运行为 76.00 FPS；开启本地脚本分析后为 47.62／50.98 FPS，并出现超过 180 ms 的长帧。后者只验证 GDScript 计时与本地输出的组合影响，不能代替编辑器远程分析器的单变量对照。

**当前更值得继续拆测的是每显示帧执行的动画／部件提交，以及 PathBudget 中的拥堵处理。** 在插桩样本的持续阶段，完整原生 `move_and_slide()` 区间约为 0.155 ms／物理步，全部通路检查约为 0.121 ms／物理步。它们在开局移动阶段更贵，分别为 1.052 和 0.525 ms／步。优化顺序应随真实负载调整，不能只照抄截图的函数排名。

两个原型都保留在构建工具中，未改动生产游戏脚本：路径采样内复用原生属性读取已通过行为回归；短轴扫描已通过 47,390 项差分与边界检查，但它在早遇障碍时更慢，没有支持全局替换的稳定帧时间证据。完整数字、逐帧间隔和构建身份见[证据数据](movement-investigation-2026-09-15.json)，原生调用链见[源码核对笔记](movement-native-source-notes-2026-09-15.md)。

## 1. 截图能说明什么

| 截图数据 | 可以得出的结论 | 不能直接推出的结论 |
|---|---|---|
| 可视分析器选中帧：GPU 约 6.42 ms，Opaque Pass 约 3.81 ms | 该采样帧的 GPU 渲染成本有记录 | 不能与另一张截图的 221.58 ms 帧时间相减，也不能代表整个 CPU 帧 |
| 普通分析器：Frame Time 221.58 ms、Physics Time 31.82 ms、Process Time 22.68 ms | 出现了严重长帧；项目物理步长为 33.33 ms | 不能把三个值直接当成互斥分项相加；没有实际补步数就无法解释差额 |

Godot 4.6.3 主循环传给分析器的 Physics Time 是这一显示帧内**最长的一次物理步耗时**，不是该帧所有补步的总和。一旦长帧触发多个物理步，Frame Time 可以远大于 Physics Time 加 Process Time。本轮因此直接记录相邻 `process_frame` 之间 `Engine.get_physics_frames()` 的差值。[主循环源码](https://github.com/godotengine/godot/blob/4.6.3-stable/main/main.cpp#L4587)

普通脚本分析器与可视分析器采集不同部分；原生调用是否单列还受编辑器设置影响。本地 `--debug --profiling` 与编辑器普通分析器都会启动 GDScript 函数计时，但本地约每秒输出最近帧统计，编辑器则有服务器分项、每帧传输和历史图表等额外工作。[Godot 分析器说明](https://docs.godotengine.org/en/4.6/tutorials/scripting/debug/the_profiler.html)、[调试面板说明](https://docs.godotengine.org/en/4.6/tutorials/scripting/debug/debugger_panel.html)、[具体源码核对](movement-native-source-notes-2026-09-15.md#补充命令行-profiling-与编辑器分析器不是完整等价环境)

截图还显示错误／警告计数 83，但没有条目内容。本轮有效独立运行没有 `SCRIPT ERROR` 或 `ERROR:`，调试构建会输出现有脚本警告；这些信息不足以判断截图是否存在重复错误输出造成的额外开销。

### 隔离与计时

所有变体从同一份冻结源码派生，复制所需资源与导入结果，并用官方 Windows Release 模板导出 PCK。冻结源自当时的工作区，包含用户未提交修改，因此 **Git HEAD 本身不足以复现它**；证据另外保存输入文件、关键冻结文件、二进制及 PCK 的 SHA-256。

所有变体共享一个研究专用 user-data 目录，与正常游戏设置分离。Godot 运行串行进行；每约 5 秒检查相关 Godot 进程，观察到的后台 Godot 只有正常编辑器。它仍可能消耗资源；没有声称操作系统全部后台负载被排除。命令行观察本身也有少量开销。

显示帧时间来自实际墙钟间隔，不使用 `--fixed-fps` 测 FPS。功能回归才使用无头／固定步进。GPU 时间由异步渲染查询取得，不保证与同一行墙钟样本严格对齐。SceneTree 前后标记只覆盖场景回调，不覆盖主循环外的全部原生服务器工作。

前四个有效运行 `baseline-1`、`profile-1`、`debug-1`、`profiler-1` 尚未加入运行前哈希断言；本轮结束后重新核对其冻结源码／PCK／二进制均与构建回执一致。这是事后身份核对。后六个运行另有运行前哈希记录，证据数据明确区分两者。

|---|---:|---:|---:|---:|---:|

| 调试构建，未开 profiler | 76.00 | 17.584 | 19.033 | 27.870 | 1 |

## 4. 移动热点的实际组成

以下来自 `profile-1`，统一以**实际物理步数**归一化；开局 241 步、持续 600 步、近景 360 步。

| 测量区间 | 开局 ms／步 | 持续 ms／步 | 近景 ms／步 | 解释 |
|---|---:|---:|---:|---|
| 原生 `move_and_slide()` | 1.052 | 0.155 | 0.086 | 直接包围原生调用的计时，不含之后写统计表的成本 |
| 全部 `has_clear_corridor()` | 0.525 | 0.121 | 0.116 | 每次调用只归入一个退出分支，允许在这组内部求和 |
| `PathBudget.next_position()` | 1.732 | 0.273 | 0.268 | 包含嵌套通路调用和其写统计表的开销 |
| `PathBudget._physics_process()` | 0.703 | 1.699 | 1.750 | 包含队列、共享路径处理及 `combat_approaches.tick()` 等工作 |

这些区间相互嵌套，**不能把表格纵向相加，也不能用父区间减子区间宣称得到生产代码的纯自身成本**。高频 Dictionary 统计和计时调用本身会扰动父区间。它们用于辨别调用规模和分支分布，候选收益仍以未插桩运行判定。

### 4.1 原生角色移动

开局 52,917 次原生移动中，52,561 次没有返回滑动碰撞、356 次返回 1 个；持续阶段 13,418 次中，12,770 次为 0 个、648 次为 1 个。三个阶段均没有观察到 2 个或 3 个以上的返回碰撞。零碰撞仍会做原生查询；碰撞结果数量也不是精确查询迭代数。

现有角色已经使用 `MOTION_MODE_FLOATING`、单胶囊、`collision_mask=3`，人物转身只旋转视觉根节点；低安全速度已跳过原生移动。密集单位之间主要由避让处理，并非这些角色碰撞体相互做成对接触求解。`max_slides=6` 是上限，无碰撞时首轮即退出。本负载没有支持降低该上限的证据。[当前角色场景](../scenes/unit.tscn)、[当前移动逻辑](../scripts/battle_unit.gd)、[Godot 浮动移动源码](https://github.com/godotengine/godot/blob/4.6.3-stable/scene/3d/physics/character_body_3d.cpp#L399)

原生细分包括重叠恢复、扫掠、接触提取和变换提交。若将来捕获到墙角密集移动且原生成本确实占据预算，再单独测这些阶段；当前不调整 `safe_margin`、Jolt 恢复迭代数或碰撞层。[Jolt 查询实现](https://github.com/godotengine/godot/blob/4.6.3-stable/modules/jolt_physics/spaces/jolt_physics_direct_space_state_3d.cpp#L861)

### 4.2 通路检查和路径采样

`PathBudget.next_position()` 负责消费现有路径、判断是否失效、进行可见捷径采样；真正的原生路径请求在预算队列中执行。持续阶段预算器现有 `query_usec_this_tick` 计时平均约 0.000205 ms／步；这个区间包含直线路由／原生查询和路径重置，不能标成纯原生 A* 时间。路径采样次数也不等于原生请求次数。[路径预算实现](../scripts/path_budget.gd)

直接追击的正向空地证书命中率为开局 73.3%、持续 78.4%、近景 78.7%。因此“添加通路缓存”不是从零开始的优化。当前证书复用有地图、拓扑、半径和包含范围约束，必须保留。[通路检查实现](../scripts/construction_navigation.gd)

路径捷径尝试没有复用该证书：`PathCorridor.next_position()` 先试最终点，再试最多 12 个较远路径点，必要时检查已越过路径点的连接。持续阶段对最终点的失败检查有 7,340 次，对候选点的失败检查有 2,819 次；它们分别扫描 15,167 和 3,577 行，平均约 2.07 和 1.27 行即拒绝。开局所有单次扫描的最大行数也只有 12。**这个真实样本的突出特征是大量短失败检查，长距离扫描并不占主导。**[路径走廊实现](../scripts/navigation/path_corridor.gd)

## 5. 两个已验证原型

### 5.1 原型 A：单次路径采样复用属性读取

修改点为 `scripts/path_budget.gd` 的 `next_position()`，约 306 行后。原型由[构建变换](../tools/movement_path_candidate.py)生成，仅改冻结副本。

具体做法：在当前调用中保存强类型 `NavigationAgent3D`，只读取一次 `path_desired_distance`、`path_max_distance`、`unit.global_position`、`unit.radius`；沿用这些局部变量完成路径点采样和偏离路径判断。缩小脚本到原生属性的重复访问，不引入跨帧状态。

必须保留的顺序是：**地图迭代号和建筑拓扑检查 → 同 tick 已采样判断 → 本次局部读取 → 路径消费 → 偏离检查 → 保存 sampled_tick**。不能把 `sampled_tick` 的快速返回挪到版本检查前面；同一 tick 内建造／拆除仍可使旧结果失效。导航层不为 1 时仍沿原生路径走廊，不使用建筑占用网格做捷径。

| Release 变体 | 开局 FPS；P95 ms | 持续 FPS；P95 ms | 近景 FPS；P95 ms |
|---|---|---|---|
| 基线 1 / 2 | 89.75 / 83.03；18.811 / 20.978 | 102.95 / 103.90；14.976 / 14.942 | 108.50 / 98.90；14.285 / 15.606 |
| 路径局部读取 1 / 2 | 89.49 / 83.88；18.856 / 19.558 | 111.86 / 111.50；14.686 / 14.392 | 126.28 / 111.68；13.051 / 14.170 |

两次持续 FPS 都高于两次基线，是值得保留的候选信号；但完整采样入口在插桩持续阶段只有约 0.273 ms／物理步，不能据此声称几个属性读取独立带来了约 8% 的游戏提速。近景波动、交战事件差异和帧率对模拟轨迹的影响尚未消除。上线前需要更紧密的重复交替运行及调用区间计时来确认收益。

行为验证：移动导航 1,034 项、路径预算 94 项、导航启动 15 项，共 **1,143 项通过**。三组移动队伍均到达，未出现路径反向；同时检查了同 tick 拓扑失效、路径预算和启动流程。

### 5.2 原型 B：选择较短的网格扫描方向

修改点为 `ConstructionNavigation.has_clear_corridor()` 的逐行扫描。保留非法输入、正向证书、边界、O(1) 空矩形检测和原有近水平处理；仅在 X 覆盖格数小于 Z 时转置扫描公式，按列检查同样的保守身体扫掠区域。每次仍使用现有二维前缀表的四次读取。[原型和插桩变换](../tools/movement_corridor_probe.py)

保留 `radius + 0.001` 的扩张和 `floor + 1` 边界规则。新增垂直退化处理只针对 `delta_x == 0`，不另加会扩大拒绝区域的 epsilon。数学上的转置不自动保证浮点边界逐位等价，因此用真实源码抽取的参考函数做差分。

47,390 项差分与边界检查全部通过，覆盖四种固定网格上的随机端点查询、端点互换、零长度、多种半径、格线与身体擦边、接近 float32 精度的扰动、非法参数、证书和拓扑变化；总数中有 17 项直接断言，其余为两函数结果对照。另有 **1,143 项**完整移动／路径行为回归通过。它们是本轮测试覆盖内的证据，不是对所有浮点输入的形式证明。

微基准使用无头调试构建，只测 CPU 查询批次；每批 2,000 次、每组两轮 ABBA、五组共 80,000 次计时查询。以下为每次调用的批次中位成本，包含相同的调度和校验和开销，不能换算为整场 FPS。

### 5.3 缓存方案的明确边界

不缓存“上次这个目标不可达”作为本次结论：起点移动、目标改变和拓扑变化都可能使旧结论无效。为每个候选保存一套大缓存表，会增加当前大量短失败检查的固定成本。

较小的待评估方案是**失败行提示**：保存上次失败行，当前查询重新用原公式算这行的 `[left, right)`，并重新查当前前缀表。如果本次仍有障碍，可以提早拒绝；否则继续原扫描。它只改变检查顺序，不复用旧可达性结论。正向证书仍最先使用，提示绑定地图／拓扑／半径，且必须落在本次扫描范围内。

准入前先测提示命中率和实际能跳过的行数。当前多数失败本来只有一两行，提示检查可能更贵，因此本轮没有新增此状态。

更复杂的“阻挡格证据”还需找到真实被占据的格，不能把失败区间的 `left` 当成阻挡格。用扩张后的原生 `AABB.intersects_segment()` 验证当前扫掠在数学上可行，但它的擦边规则尚未证明等价于现有扫描；返回值应与 `null` 显式比较。该方案当前排在失败行提示之后。[Godot AABB 文档](https://docs.godotengine.org/en/4.6/classes/class_aabb.html#class-aabb-method-intersects-segment)

## 6. 下一步优化的实施顺序

### 第一优先：对齐慢帧负载，缩小测量扰动

在相同摆阵、地图位置、自然生命规则下保存出生列表和命令序列；对照 Release、调试未开分析器、编辑器单独开启普通分析器三种环境。始终记录 P95／P99、最大帧、每显示帧物理步数、移动／拥堵人数及伤害事件，而不是只看平均 FPS。

热点采样改成每阶段少量整段计时和预分配整数累加，避免每单位每帧更新多层 Dictionary。一次只拆一个热点族，正式对比始终用无热点插桩版本。若目标是 60 FPS，以 16.67 ms 显示帧预算评估 P95；30 Hz 物理则按每步 33.33 ms 和实际补步判断积压，这两个预算不能混用。

### 第二优先：拆分动画／批量提交，以及拥堵处理

`UnitRenderBatches._process()` 在持续阶段的插桩入口约 6.558 ms／调用，里面包含 `synchronize_animation()`、其嵌套写统计表，以及部件变换提交。动画同步累计调用 551,299 次；该数与显示帧数一起增长。这个证据支持继续拆测，**不支持直接说生产代码的批量渲染就耗时 6.558 ms**。[批量渲染实现](../scripts/unit_render_batches.gd)、[动画同步实现](../scripts/unit_visual.gd)

最小拆测区间是直接围住 `locomotion.advance()`／`attack.advance()`、单单位父变换计算、部件 `global_transform` 读取与矩阵合成、`set_instance_transform()` 提交；同时记录实际姿态采样次数和提交部件数。`advance()` 可触发显隐回调，需另计槽位变更次数，不能把整个区间都叫动画数学运算。

项目已经在 192 模型阈值后按需采样，通过 `_locomotion_advanced`／`_attack_advanced` 避免同一时钟进度重复 `advance()`；颜色、显隐和槽位已有事件维护，每单位只算一个插值父变换，批次也有 `custom_aabb`。这些已有机制不能再次作为新增优化收益。

`PathBudget._physics_process()` 的持续入口约 1.699 ms／步，而其中已解析路径请求的计时接近零。下一步应分开 `combat_approaches.tick()`、`shared_paths.poll()`、等待地图循环和路径查询循环，记录各自执行工作数／积压数。拥堵任务再拆资格判断、`_find_auto_target()` 原生查询与筛选，以及 `FriendlyPassage.request()` 的邻居查询、两侧 `test_move()` 和落点检查。这只是待验证的归因，不能把差额全部算给拥堵处理。[路径预算](../scripts/path_budget.gd)、[拥堵预算](../scripts/combat_approach_budget.gd)、[友军让路](../scripts/friendly_passage.gd)

拆测后按占比选择一个原型，具体改动边界如下：

| 候选 | 实施细节 | 必须保留的行为 |
|---|---|---|
| 部件局部姿态缓存 | 仅姿态变化时重算相对 ModelPivot 的部件变换；每显示帧仍与插值父变换合成 | 精确发射采样、暂停／入屏、死亡姿态、采样模式切换及时失效；联机副本时钟保持独立 |
| 按批次整块提交 | 为每个批次复用 `PackedFloat32Array`，比较 `MultiMesh.buffer` 与逐实例提交；分别计时数组打包和上传 | 保持颜色、淡出、容量增长和槽位交换；GDScript 打包成本必须计入，不能预设批量上传一定更快 |
| 冷却到期再处理拥堵任务 | 先测无效出队比例，再考虑前移 `_next_rebalance_frame` 检查或只让到期单位入队 | 每步最多四任务、队列公平性和执行前目标／命令复核；即时攻击和新命令仍立即响应 |

`MultiMesh.buffer` 是原生提供的整块缓冲接口；这里是待测设计，没有进行实现或宣称收益。[Godot MultiMesh 接口](https://docs.godotengine.org/en/4.6/classes/class_multimesh.html)

### 第三优先：保留小范围优化候选

| 方案 | 改动边界 | 验收条件 |
|---|---|---|
| 路径采样局部读取 | 只改一次同步调用内的局部变量；不移动失效检查 | 重复交替运行的阶段帧时间改善可重复；同 tick 拓扑、导航层、到达行为全部保持 |
| 受限短轴扫描 | 只针对实测长扫描，不破坏早期拒绝 | 真实查询回放总成本下降，早遇障碍场景不明显退化，差分边界与完整移动回归通过 |
| 失败行提示 | 重查当前行，仅提示检查顺序 | 节省行数抵消提示开销；地图／半径／版本变化后仍与原函数一致 |
| 原生移动设置 | 仅在墙边原生查询被证明占预算后单独调整一个参数 | 保持窄门、凹角、斜行、出生重叠和建造挤压行为；不以减少正确碰撞换取速度 |

在上述重复测量中，阵容存活数、移动人数、攻击事件和实际物理步数应保持可比；不能用少打了、少动了或跳过模拟的样本证明优化有效。本轮候选各两次运行不足以作统计显著性或一般性收益承诺。

## 7. 验证及复现入口

本轮 10 次正式有画面运行均完成场景检查，原型 A 与 B 各通过 1,143 项行为回归，B 另通过 47,390 项差分与边界检查；微基准五组校验和一致。所有计时原始间隔、碰撞分桶、通路分支、每秒人口观察和验证结果均保存在[证据 JSON](movement-investigation-2026-09-15.json)。

早期一次导出因附带无关测试依赖失败，另两次微基准启动方式失败；这些设置失败保留在 `.local`，未纳入上表。有效微基准使用独立验证副本中的调试可执行文件。没有用无头或固定 FPS 的功能测试帧率作为性能证据。

以下命令均从项目根目录执行。输出目录必须是新的，以避免覆盖已有证据；Godot 安装位置和模板版本在构建工具顶部定义。先构建基线，再由同一基线派生候选，测量期间不要并行运行验证任务。

```powershell
python tools/build_movement_investigation.py --output .local/movement-next/base --variant baseline
python tools/build_movement_investigation.py --output .local/movement-next/path --base .local/movement-next/base --variant path
python tools/build_movement_investigation.py --output .local/movement-next/axis --base .local/movement-next/base --variant short-axis

python tools/run_movement_investigation.py --build .local/movement-next/base --output .local/movement-next/runs --run-id baseline-1
python tools/run_movement_investigation.py --build .local/movement-next/path --output .local/movement-next/runs --run-id path-1
python tools/run_movement_investigation.py --build .local/movement-next/base --output .local/movement-next/runs --run-id debug-1 --runtime debug
python tools/run_movement_investigation.py --build .local/movement-next/base --output .local/movement-next/runs --run-id profiler-1 --runtime profiler

python tools/validate_movement_investigation.py --build .local/movement-next/axis --output .local/movement-next/axis-validation --test movement_corridor_probe_test --test movement_corridor_microbenchmark --test movement_navigation_test --test path_budget_test --test path_budget_startup_test
python tools/summarize_movement_investigation.py --runs .local/movement-next/runs --output .local/movement-next/summary.json
```

`--natural-health` 可用于自然损耗场景，必须给独立 run-id 并与同规则基线比较。`--harness-check` 只检查测试架能否运行，不纳入正式性能统计。自定义插桩需构建 `--variant profile`；它与本地 `--runtime profiler` 是两种不同的测量方式，汇总工具会分别识别并排除在未插桩对照分组之外。
