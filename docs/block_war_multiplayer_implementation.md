# 多人联机 1.1.0 实现与验证

本文件记录已落地的实现；玩法与边界约定见 [设计文档](block_war_multiplayer_design.md)。

## 玩家流程

主菜单“多人联机”进入房间。房主选择六张地图之一，固定席位对应地图原有阵营；可换到任意空位，并逐位添加电脑。所有真人分别选择指挥官、准备后，房主开始。地图、席位或角色改变会撤销准备状态，加载屏障确认所有真人进入战场才开始计时。

鼠标只向同队真人共享。它使用地图世界坐标，经各端镜头投影；经过 HUD、失焦、离开窗口或打开本地菜单时隐藏。静止时保活，旧序号、旧可见状态、过期指针和恢复控制前的指针都不会重新出现。

## 运行职责

| 文件 | 职责 |
|---|---|
| `scripts/network/war_online.gd` | Session 常驻的 ENet/DTLS 传输、令牌重连与房间接口 |
| `server/war_relay_rooms.gd` | 席位、准备、加载屏障、断线窗口、身份和流量边界 |
| `server/war_relay_server.gd` | 独立 UDP 中继；同队鼠标直接按队路由 |
| `scripts/network/war_network_match.gd` | 固定 30 TPS 房主、输入序号/控制代际、事件序列与恢复 |
| `scripts/network/war_snapshot.gd` | 完整战斗状态、可靠差量、只读镜像与平滑显示 |
| `scenes/network/war_room.tscn` | 原生房间界面和六个预搭席位 |
| `scenes/network/teammate_cursors.tscn` | 原生固定指针池，沿用游戏阵营颜色与字体 |

开房者执行全部战斗规则与 AI，中继不进行战斗计算。客户端不结算伤害、占领、出兵、生产或技能；本地菜单不暂停房主模拟。传输接口与战斗协调器分开，后续 Steam 接入可替换传输。

房主每帧最多推进 8 个固定步，长帧剩余时间留待后续帧追赶，不丢失出兵、AI 或技能计时；断线暂停期间不积累模拟欠账。10/30/120 FPS、2 秒长帧和断线恢复使用相同的规则时钟。

战斗按稳定的建筑、行军订单、士兵和火焰 ID 复制。建筑人口只在士兵实际离开时减少；订单预留人数与未出发士兵一起恢复。兔洞 50 人上限、打洞等待、归巢改道、冲刺、蛙隐身/虚弱、熊链接累计分摊余数、区域效果、建筑施工、炮弹引用与火焰已命中记录都进入镜像。

连续显示与可靠事实分离：

- 建筑受损、出兵、改道、技能、士气、阵营变化等以可靠事务提交。
- 通常每 0.5 秒发送绝对位置修正，分帧发送；每包最多 32 名士兵，只包含毫米精度路程与共享时刻，控制包不承载技能状态。
- 客户端从已知路线短暂外推；单个锚点最多外推 1 秒，小误差用约 80 毫秒视觉偏移收敛，不预测死亡或占领。
- 私有技力与冷却按玩家单独发送，不向其他客户端广播。
- 校验只针对可靠镜像；显示锚点不参与校验。数字校验归一化至小数 8 位，消除 Godot JSON 整数/浮点类型与末位舍入差异；实际规则和恢复数据仍保留完整浮点精度。
- 大事务和快照以有界压缩数据分块传输。快照包含可靠基线与独立的新鲜显示基线；同时到达的后续事务按序接上，旧快照不能倒退状态。
- 位置修正有每秒 400 包预算，上一轮全部发完才开始下一轮，避免大军团尾部长期收不到修正。快照按每秒 128 KiB 分帧发送，单份未压缩状态上限 8 MiB、可靠待发队列上限 48 MiB；超限时明确结束连接，不丢弃战斗事实后继续运行。
- 最终结果等待最后一笔战斗事务应用完成，避免结束界面截断最后一次占领。

## 生命周期

普通玩家断线 10 秒后由房主 AI 接管，120 秒内可凭内存中的重连身份返回。恢复先装入快照、追上事件，再确认新的控制代际；过期命令不能补发执行。房主断线暂停，30 秒内同一进程可恢复；主动离房或超时结束房间。首版没有房主迁移。

恢复快照结束时附带最新事件边界，客户端追到该边界才确认恢复和开放操作。新连接取消旧连接未完成的快照；未开始发送的重复快照可合并，已经开始的传输不会被普通重同步请求反复重启。加载期间断线也会重新确认加载屏障。重连令牌在客户端确认前保留上一代，避免单次确认丢失后无法再连接。

所有客户端使用受信证书验证 DTLS，不使用不验证身份的 TLS 选项。六条低层原生通道分别承载房间、命令、可靠事件、鼠标、位置修正和快照。中继校验身份、阵营、消息种类、通道、数值与大小，且有包数/字节预算。重连凭据、SSH 密码及服务器私钥均不进入仓库或客户端包。

## 可重复构建

客户端和中继固定使用 Godot **4.7.2**，避免 4.6.3 的 DTLS 连接销毁问题。运行时与导出模板由 `tools/deploy_block_war_relay.py --runtimes` / `--templates` 下载并核对官方校验；保存在 `.local/network`，不改用户的编辑器安装。

```powershell
python tools/build_network_manifest.py
python tools/build_network_manifest.py --check
./tools/build_windows.ps1 -VersionedOutput 1.1.0
```

构建脚本重新生成规则/地图/路线内容指纹、验证资源引用、导出并从 PCK 加载全部六张地图。文本指纹按仓库的 LF 换行规范计算，避免 Windows 工作区与干净克隆内容相同却无法联机；二进制路线保留原始字节。正式包测试从空资源目录启动，使用绝对 PCK 路径，防止源目录替导出包补足遗漏的文件。客户端仅包含信任证书公钥和内容清单，排除服务器、测试、工具、私钥、临时备份和本地配置。

## 本轮验收记录

规则和复制检查通过：完整快照 1217 项、战斗接入 70 项、可靠复制 45 项、固定时钟 181 项、4096 人负载 10 项。原生房间 UI 72 项、正式 Windows 包 53 项通过；既有出兵、输入、建筑、队伍与各角色技能回归通过。

传输检查通过：房间模型 120 项、本地原生 DTLS 41 项、六客户端双房间 31 项、证书拒绝 6 项。使用 UDP 代理注入两档弱网：5% 丢包/150 ms 往返延迟/35 ms 抖动/2% 重复，及 10% 丢包/300 ms 往返延迟/60 ms 抖动/5% 重复，均通过 33 项检查。它们用于检验有损传输与恢复，不代表所有网络环境的延迟保证。

东京中继已部署在 UDP 42300，独立 `block-conquest-relay.service`，专用低权限用户运行 Godot 4.7.2 release。默认最多 8 个房间；内存软限 128 MiB、硬限 192 MiB。原有 `arc-nice-relay` 和 `bot-jump-relay` 的进程与服务实例保持不变。正式内容指纹的公网 DTLS 验证通过 39 项。

正式 PCK 从空资源目录连接东京中继，三客户端实战验证 85 项通过（房主 38、队友 29、敌方 18）。覆盖非零席位房主、电脑补位、真实出兵、兔子冲刺/归巢/兔洞、熊四技能、同队鼠标、短断线、超过 10 秒的电脑接管、房主断线暂停与恢复，以及最终可靠状态摘要一致。客户端由同一电脑的三个独立进程运行，未声称已完成不同外网设备之间的测试。

Godot 4.7.2 的 4096 单位压力检查通过 10 项；本机无头、单进程双场景测试中，房主模拟与发布平均约 30.9 ms，客户端收包约 0.8 ms、展示约 22.1 ms；双场景合计平均 53.8 ms、峰值 79.1 ms。内存传输恢复约 225 ms，位置修正约 207136 B/s、300 包/秒、最大 759 B（带宽包含每包 100 B 的封装估算）。这是本地压力基准，不是公网恢复延迟，也不代表 4096 人时可稳定 60 FPS。

公网实战后测试房间和连接均归零，服务无重启，RSS 约 34.1 MiB、峰值约 75.3 MiB。服务无脚本错误；客户端退出后 5–11 ms 出现原生 DTLS `-30464` 关闭诊断，实战、重连与最终状态校验均在此前通过。保留该诊断记录，不将服务器日志描述为完全零错误。
