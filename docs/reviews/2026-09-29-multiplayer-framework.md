# 多人框架深度审查

审查日期：2026-09-29。主要基线：`6613a67`，Godot 4.7.2。范围覆盖客户端传输、Relay 房间模型、权威命令、可靠复制、状态恢复、房间 UI 与场景切换，并针对已确认缺陷修复和回归。

## 结论

现有框架适合继续迭代 2–6 人房主制对局。身份、控制代际、可靠事件顺序和断线恢复已有明确边界，不需要推倒重写。此次确认并修复三项问题：持续交战放大全军可靠同步、加载阶段重叠断线造成屏障卡住、房间请求在握手及重连时重复发送。

仍有一个已确认的协议信息边界缺口：客户端收到敌方精确人口与隐藏军令。大规模战斗的 CPU 余量也不足，不能依据当前测试承诺 4096 人稳定 30 TPS／60 FPS。下文将已修缺陷、未修设计缺口和容量限制分别列明。

## 已确认的问题

### [P1，已修复] 未跨星的士气变化触发全军可靠重发

位置：`scripts/network/war_snapshot.gd` 的 `diff()`。

旧逻辑只要士气原始点数变化，就判定移速改变，把所有单位重新写入可靠事务。击杀、损失或士气衰减都可能频繁触发，即使星级和实际移速完全没有变化。原压力回归以行军为主，没有检验这种交战模式。

通过真实战斗抵达回调，每 tick 让守方获得 10 士气，连续 30 tick；场上另有 4096 名士兵。守方士气始终低于 500，移速没有变化：

| 指标 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 全军可靠更新次数 | 30 | 0 |
| 产生的原始可靠规则数据 | 12,779,875 B | 11,071 B |
| 最大发送队列积压 | 1,459,992 B | 0 B |

表中是这一受控场景的原始序列化量与应用队列，不能当作公网带宽或所有战斗的降幅。现在只在实际升降星时重新锚定全军，保留士气点数、建筑伤害及表现事件的正常可靠提交。跨星两个方向、移动区域开始／消失仍执行必要的重新锚定，客户端最终摘要一致。

### [P2，已修复] 双方重叠断线后，已完成加载的客端确认丢失

位置：`scripts/network/war_online.gd` 的 `member` 分支；服务端加载屏障在 `server/war_relay_rooms.gd`。

复现：进入 loading → 房主断线 → 客端也断线并在离线时完成场景加载 → 客端先重连，收到 `host_lost` 房间 → 房主恢复。旧客户端仅在 `loading` 重发记忆中的完成确认，所以服务器一直缺少客端确认，最终到加载期限后返回房间。手动补发同一客端的 `loaded()` 可以立刻开局。

现在同一对局已完成加载的重连成员，在 `loading` 或 `host_lost` 都补发确认。Relay 继续负责判断有效阶段，不会在房主缺席时提前开始。正式原生 DTLS 测试覆盖此交叉顺序。

### [P2，已修复] 握手和入房确认前重连重复发送 create／join

位置：`scripts/network/war_room.gd` 的 `_request()`、`_state_changed()`，以及 `war_online.gd` 的 `welcome` 分支。

旧 UI 在 `connected` 同步回调中发送待办，Online 的 welcome 流程随后又发送同一意图。玩家成功入房却看到“已在房间中，请先离开”。仅交换 welcome 内的顺序还不足以覆盖入房确认前的重连，因为 UI 和 Online 都保留待办并各自重发。

修复后，用户动作只向 Online 提交一次意图，Online 统一管理握手与重试，UI 不再通过连接状态回调重建请求。新增真实场景加房间模型的回归，同时覆盖 create、join、预排队 API 调用和确认前重连。

### [P2，未修复] 隐藏驻军和未暴露军令仍发送给非房主客户端

位置：`scripts/network/war_snapshot.gd:116` 的 `for_player()`，以及 `capture()` 的 buildings／orders／units 字段。

`for_player()` 只清除其他玩家的技力和冷却，建筑精确人口、门内队列、完整军令目的地和路线仍进入客户端。已有真实序列化镜像中，阵营 2 的客户端可以直接读取敌方阵营 1、3、5 的各 60 人驻军。正常 UI 隐藏数字及 AI 不读取这些值，并不能阻止修改客户端获取它们。

建议下一阶段先定义“权威完整状态”和“按接收阵营裁剪的观察状态”：敌方人口不下发，门内／地下队列及未暴露军令不下发，公开表现效果单独明确可见范围。事件、位置锚点、恢复快照及其摘要必须使用同一可见性合同；预约人数一致性校验也要调整，不能只把一个人口字段写成零。

本次没有改写整套接收者副本与校验协议。房主本身继续掌握完整权威状态；若要求连房主也无法作弊，需要另行采用可信专服，单靠裁剪普通客户端数据无法解决。

## 健壮性评价

| 边界 | 审查结果 |
| --- | --- |
| 身份和控制权 | Relay 按连接绑定玩家，Host 收命令和执行命令时均检查席位、控制者、连接状态及 epoch；重复序号不重复扣费执行。 |
| 跨通道顺序 | 事件有独立序号，完整快照携带可靠基线与恢复追赶边界；位置锚点不能提前应用尚未知晓的结构变化。 |
| 重连 | 普通客端、房主和加载阶段有不同恢复窗口；进行中的快照受保护，同一玩家重同步有 1500 ms 限流。没有把请求频率直接变成快照生成频率。 |
| 私有账户 | 技力／冷却单独发送；同 tick 用事件边界排序，避免暂停或投降更新倒退。 |
| 异常数据 | JSON 类型、深度、节点预算、大小、数值和引用有校验；快照有原始大小和压缩大小上限，应用发送队列有容量限制。 |
| TLS | 本地测试确认不受信证书及错误服务器身份被拒绝；没有通过关闭身份验证让测试通过。 |

未开展公网压测、跨设备实战或多房满载测试。脚本包大小限制是在原生 ENet 重组之后执行，不能把它当作原生重组内存上限；未入房连接也可以保持在线，占用连接池。这些属于还需专门验证的资源边界，本次没有做 OOM 攻击实验，不将其写成已经实证的漏洞。

## 性能与规模

增强压力回归至 120 个采样帧，报告各阶段均值、P95、P99 和最大值。环境为本机无头、单进程内 Host 与一个客户端双场景、4096 士兵、内存序列化传输；没有 GPU 渲染及公网 RTT，测试帧耗时不是玩家最终 FPS。

| 阶段 | 平均 ms | P95 ms | P99 ms |
| --- | ---: | ---: | ---: |
| Host 模拟与发布 | 34.83 | 36.38 | 85.25 |
| 客户端接收 | 1.92 | 3.68 | 50.76 |
| 客户端呈现 | 30.10 | 53.03 | 53.85 |
| 双场景合计 | 66.87 | 91.80 | 162.60 |

该次恢复约 235 ms；位置锚点估算约 208,780 B/s、304 包/s、最大 759 B，包含测试固定封装预算。位置流和规则流必须分开看，旧的士气问题发生在可靠规则流，不能用锚点带宽正常来排除它。

后续优化优先级：

1. **减少每 tick 全量分配和扫描。** `capture()` 每步重新构造所有单位记录，`diff()` 再扫描整份状态；持续单位数量增长时，分配和比较成本随之增长。先区分离散脏记录和可替换连续状态，再保留完整恢复捕获。
2. **降低摘要及完整候选校验的尾延迟。** 两秒一次的摘要递归归一化并序列化整份可靠镜像；每笔事件应用后也重新验证完整候选状态。应基于不可变行及明确的引用依赖做增量校验／摘要缓存，同时保留完整快照入口校验。
3. **增加真实战斗负载和不同规模基准。** 4096 人行军、持续交战和频繁范围技能应分别记录 CPU、队列高水位、端到端控制延迟；再扩展到六真实客户端、多房及弱网，避免只提高容量常量。

## 可扩展性评价

房间规则 `war_relay_rooms.gd` 与原生传输分离，对局协调器也通过 Online 的信号／方法收发，现有内存传输测试证明了替换接缝。未来接 Steam 传输有基础，但仍需为连接状态、可靠顺序、重连身份和错误路径定义显式适配合同。

主要维护压力集中在 `war_network_match.gd`（约 760 行）和 `war_snapshot.gd`（约 720 行）：前者同时管理权威时钟、命令、事务、恢复分块和表现，后者同时承担捕获、数组字段编码、校验、恢复及显示预测。新增英雄、字段或可见性规则，需要同时检查多处位置索引和分支。

建议按风险分阶段整理：先建立接收者观察状态合同，再拆出可靠事务流和快照传输生命周期，最后把重复的字段索引与记录验证集中为明确的 schema 定义。保留稳定 ID、房间模型和现有真实场景测试；没有必要把数千民兵改成逐节点同步。

## 验证记录

14 个正式测试脚本共 **2379 项检查通过**，包括快照边界、可靠复制、地形高度、对局控制、4096 人压力、士气交战、握手 UI、固定时钟、原生 DTLS、六客户端负载和证书拒绝。另有协调器生命周期探针 **9 项通过**：保留真实 Online 节点，分别退出已开局房主、已开局客端和加载中的房主场景后，协调器弱引用均失效，五种信号连接各由 1 降至 0，再次发信号无错误。

固定时钟测试原有六项末尾断言已过期：建造曾奖励 50 士气，但在 20 秒结束前合法衰减为零。此次改为逐 tick 记录建造、完工和士气峰值，保留每个场景 600 tick、10／30／120 FPS、长帧、菜单和断线下的全部状态摘要比较，并将 AI 技力需求及支出历史纳入摘要。修订后为 **193 项通过**，没有修改模拟逻辑来迁就旧断言。

静态扫描 225 个运行时源文件，没有产品边界或资源引用错误；本轮差异通过空白检查。原生日志存在当前环境根证书存储读取诊断，证书拒绝测试也会产生预期 TLS 诊断；测试通过不代表引擎日志完全没有错误文本。

网络指纹使用当前提交基线的文件，只覆盖本轮三个运行时脚本，再由原始构建工具在隔离输入目录校验：119 个输入文件，变更仅涉及 `war_online.gd`、`war_room.gd`、`war_snapshot.gd`。并行任务尚未提交的地图变更未混入指纹；因此这里验证的是本轮提交内容，而不是包含进行中地图工作的整个工作区。

最终逐项结果、性能数据和本地日志摘要见 [验证记录](2026-09-29-multiplayer-framework-verification.json)。本轮没有部署或修改公网 Relay。已通过进程命令行核实本轮测试进程全部退出，保留用户编辑器及其运行中的大厅。用户现有 `project.godot` 编辑器格式化变更、地图任务修改及其他未提交文件保留。
