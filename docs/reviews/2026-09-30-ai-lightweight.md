# AI 轻量化：重复评估与集中决策成本

本轮基于 `035db7c` 继续优化 AI，前一轮选敌、伤害基础倍率和场域几何缓存的收益不重复计入。问题主要在决策时反复扫描相同士兵、计算相同倍率和预测相同坐标。五方 AI 每三秒集中决策，会把这些成本叠加到一个更新中。

## 已落地的改动

- 防守观察一次扫描已知军队，同时产生来兵计数、按目标分组的威胁。没有来敌的建筑不再逐个扫描全军和计算倍率。每个目标内部保留原单位顺序、阵营顺序和两次伤害加法。
- 战略评估复用本次决策的敌方距离；征服候选复用与出发建筑、派兵比例无关的铁匠及防御加成。浮点缓存使用 Float64，原乘除顺序保留。
- 技能完全不可施放时跳过评分，仍按原规则推进下次决策时间。松鼠先筛选真正需要预测的敌兵；加速候选复用每名符合条件士兵的前瞻坐标；青蛙、熊提前筛选有效炮塔；火焰路径提前转换水平坐标。
- 松鼠、猪、熊、兔在各自一次技能评估内复用同目标、同阵营、同技能加成的战斗倍率。没有合并士兵强度，也没有改变逐兵累加顺序。
- 猪的各条技能派兵候选复用相同来源、相同兵数的原始出门排队时间，再按原式修正密集编队。青蛙对同候选、同士兵只计算一次水平距离，三个技能分别按原兵员顺序累加双精度分数。兔的多个炮塔评估复用四秒前瞻坐标，多个地道候选复用同目标的已投入兵力。

快照和倍率缓存仅供一次不修改战场的评估使用。策略观察发生在技能施放之后，不能把施法前的快照交给施法后的策略，也不能跨 AI 阵营共用。技能、出兵、施工和后续回合仍读取当时的真实状态。决策频率、评分、候选顺序、技能数值、信息边界和行动规则保持不变。

## 测量方式与结果

使用 Godot 4.6.3、真实群岛长滩场景、六阵营、初始总人口 1800，每阵营额外转换一座三级前线炮塔。每个变体推进 3000 次固定 `1/60` 秒控制器更新，从对局 100 秒推进至 150 秒。固定完整 `035db7c` 的三个 AI 脚本为基线；选敌、场域及其他规则在两边均使用当前版本。

松鼠场景三轮串行顺序为 A/B、B/A、A/B。每次更新记录经过时间；每个 AI 决策更新结束后，在计时外保存精确快照和 AI 内部规则状态。每轮 17 个 AI 决策更新，每个更新依次执行五方 AI。

| 指标 | 原 AI（三轮） | 本轮优化（三轮） |
| --- | --- | --- |
| 每次五方决策平均耗时 ms | 40.870 / 42.940 / 42.547 | 24.071 / 25.252 / 24.322 |
| 五方决策最高耗时 ms | 98.503 / 93.922 / 98.649 | 49.706 / 47.307 / 59.189 |
| 控制器平均更新 ms | 3.858 / 3.884 / 4.068 | 3.989 / 3.859 / 3.934 |
| 控制器最高更新 ms | 123.104 / 118.835 / 128.535 | 84.250 / 80.161 / 92.063 |

三轮合并后，AI 决策平均耗时降低约 **42%**；三轮峰值的中位数降低约 **50%**。摊到全部更新，AI 阶段约 **0.239 → 0.139 ms/更新**。AI 的主要问题是集中决策尖峰，不能据此把所有持续卡顿都归因于 AI。控制器平均耗时没有稳定的显著改善，因此本轮不声称整体 CPU 或 FPS 获得同等幅度提升。

计时包含系统调度等待；本轮曾观察到很重的其他后台计算，完整保留初步与最终样本，不挑选最好的一次。运行器另外记录 Windows `GetProcessTimes` 的完整子进程用户态/内核态 CPU 秒数，明确区分于 AI 阶段计时；该值包含启动、快照、全线程和清理，不能作为 AI 耗时。松鼠最终三轮完整子进程 CPU 平均约 15.146 → 14.974 秒，变化很小。

## 验证范围

伤害专项共 6798 项，覆盖普通与混合强度、冲锋、冲刺、加速/减速、雾、隐身、待出兵、死亡、悬浮、护盾和熊守护，逐观察阵营、逐建筑比较浮点精确值。新增 550 项生命周期检查覆盖建筑易主、敌军显示变化、施法后观察、护盾到期、暂停恢复、快照隔离及征服候选环境加成的精确一致性。

第一阶段六英雄 A/B 均通过；但猪、青蛙、兔分别仍有约 159、167、130 ms 的 AI 峰值，因此继续优化了上述三个英雄的专用方法，并单独进行三轮复验。松鼠数据不能代表所有英雄的性能上界。第二阶段未改动其他英雄执行路径，共享逻辑仍沿用第一阶段验证版本。各阶段源码哈希分别保存。

包括分项归因和已被后续优化替代的第一阶段实验，本轮共 **20 组 A/B、40 个进程、340 对 AI 决策检查点**全部精确一致；每组逐更新规则计数、初始和最终状态也一致。不能从此推导所有地图与所有技能组合已经穷举。

松鼠详细模式中，完整 3000 次更新内 `combat_multiplier` 实际调用从 **6386 → 495**，减少 **92%**。该计数包含模拟战斗调用，不是单独的 AI 调用次数；只有 AI 模块在 A/B 间变化。征服评估总耗时降低约 40%，加速选点评估约 76%。细分阶段互相嵌套，不能相加，也不和普通模式计时直接比较。

伤害、快照生命周期、AI 信息边界、策略、技能、能量塔策略、猪 AI、士气、复制、未来运动和规则边界，共 11 项回归套件、9557 项检查通过。回归使用 4.7.2；所有性能及完整英雄状态对照使用用户当前版本 4.6.3。网络兼容清单已更新。

旧 `--baseline-ai-information` 开关也补充了批量观察适配，确保调用路径变化后仍实际执行冻结算法；额外 600 次更新的旧模式 A/B 精确一致。全部验证完成后通过系统进程命令核实：Godot、测试用 Godot 和相应 Python 验证进程均为 0。

## 限制与复现

测试手动调用真实控制器 `_process`，属于无头 CPU 对照，不是完整引擎帧或实机 FPS 测试。没有完整推进 Tween、子节点正常帧处理、GPU 渲染或真实长帧 delta 的反馈。决策检查点覆盖每次五方决策完成后的状态，未声称记录了每个事件的完整顺序。

剩余峰值包括真实施法、首次场域采样和五方行动集中执行。青蛙、兔在本轮场景中仍有 120～138 ms 的决策峰值，仍值得继续治理。没有通过延迟决策、削减候选、减少士兵或改变技能效果换取测试结果。当前不能宣称已消除卡顿或保证稳定 60 FPS。

```powershell
python tools/profile_block_war_singleplayer.py --godot 'C:\Program Files\Godot\Godot.exe' --ai-lightening both --ai-commander squirrel --front-towers --frames 3000 --rounds 3 --timeout 180 --out .local/ai-lightening-final-squirrel
```

`--ai-commander` 支持 `squirrel/pig/fox/frog/bear/rabbit`。`--ai-lightening strategy` 或 `skills` 分别替换相应模块和其共享 information 依赖，不能把两组收益相加；`--detailed-ai` 增加嵌套阶段计时和调用计数，其时间不与普通模式直接比较。
