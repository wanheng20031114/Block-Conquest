# 联机大兵量 CPU 优化实验

本轮已完成逐项验证和生产优化：采纳 B、C2、D，拒绝更慢的 A，并用 C2 替代有额外开销的 C1。三轮完整联机流程 A/B 显示，4096 名背景士兵的高程地图场景中，房主处理平均耗时降低 18.5%–25.7%，加入端收包与每帧处理合计降低约 7.1%–12.7%。27 个原有回归脚本共 4493 项检查通过，最终原生行军验证 48 项检查通过。这个极限负载仍有明显 CPU 瓶颈，不宣称稳定 60 FPS。

| 方案 | 决定与当前状态 | 独立证据及边界 |
| --- | --- | --- |
| A：整块 MultiMesh buffer 提交 | 拒绝，未应用生产 | 数据等价通过；原生 `_render` 平均慢 13.3%–17.0% |
| B：同步调用内合并重复提交 | 已合入并通过集成 | 重复提交操作平均耗时降低 10.5%–24.9%；普通单步持平；原生 581 项检查通过 |
| C1：所有零偏移单位提前返回 | 被收窄为 C2，未采用此版本 | 零偏移场景受益，但平地／空中非零控制组有额外开销 |
| C2：仅高程地面分支跳过零偏移重投影 | 已合入并通过集成 | 高程地面全零平均降低 56.9%–57.7%，半数为零降低 26.7%–27.6%；非零高程地面仍约 1% 判断开销；无头／原生各 508 项检查通过 |
| D：跳过零时长范围积分 | 已合入并通过集成 | 有零积分段时平均降低 7.8%–33.0%；部分冲锋控制组增加约 0.3%；271506 项检查通过 |

初始实验基线为 `de06d2210bae734addce5ef2166a5d5c5e4d9dce`。候选脚本在 `.local` 独立生成，测量记录保存具体源码哈希；没有通过降低兵力、模拟频率、同步频率、规则检查或视觉效果来换取数据。独立实验的结论与最终生产组合的结论分别记录。

## 方法、证据范围与帧率说明纠正

引擎为 Godot `4.7.2-stable (official)`，CPU 为 Intel Core i7-14700K。P0、B、C、D 的阶段性能数据采用无头模式；A 另在私有 Windows 桌面、Vulkan Forward+、NVIDIA GeForce RTX 3080 Ti 上运行。性能实验由主线程串行调度，正确性检查、状态哈希和原生资源读回不放进 A/B 的内部计时段。计时来自 `Time.get_ticks_usec()`，属于指定 CPU 调用区间的墙钟耗时，包含可能的调度和引擎同步阻塞，不是硬件性能计数器给出的纯 CPU 执行时间。

表中的“平均 / P95”单位均为毫秒。P0 是一次运行的样本统计；A、B、C、D 的汇总是三轮平均耗时的算术平均，以及三轮各自 P95 的算术平均。后者不是合并全部原始样本后重新计算的 P95。不同实验的夹具、调用频率和统计范围不同，不能把它们的阶段耗时直接相加。

需要纠正 `docs/reviews/2026-09-30-client-motion.md` 中“窗口运行器限制实际绘制速率为 24 FPS”的表述。运行器确实传入 `--max-fps 24`，但自动加载的 `Session/Settings` 会在 `game_settings.gd::_apply_values()` 中执行 `Engine.max_fps = fps_limit`，默认值为 120；自动化启动只跳过窗口尺寸等设置，没有跳过帧率和 VSync 设置。本轮 A 的原生运行实际记录为 `Engine.max_fps=120`、VSync 模式 1，帧墙时约为 16.5–16.7 ms，明显受到显示同步影响，不能称为实际固定 24 FPS。

旧 motion 运行器还会在没有 `--real-time` 时传入 `--fixed-fps 24`，这是引擎虚拟时间步设置；motion 测试本身另以显式 `1/60` 秒推进被测逻辑。仅凭这些参数不能追溯旧运行的真实显示 FPS。本轮保留旧 JSON receipt 的原始内容，并在旧 Markdown 报告加入明确勘误；旧逐虚拟步的位移、步态和事件等价结论仍应按其原有时间模型理解，不能升级为真实 60 FPS 证明。

原生验证使用的是 **MultiMesh 资源数据读回**：在实际渲染器运行后，通过 `get_instance_transform()` 和 `get_instance_custom_data()` 比对资源中的变换、颜色与步态。它不是像素比较，也不是 GPU 着色器执行结果验收。`RenderingServer.frame_post_draw` 不是 GPU 完成栅栏。无头虚拟渲染器不能提供同等读回证据。本轮新说明已采用上述准确名称；旧 receipt 中的 `gpu_readback` 等字段名保留原样，不据字段名称扩大证据范围。

## 候选 A：整块 MultiMesh buffer 提交，拒绝

候选保留原有朝向、缩放、地形表现位置、线性颜色和步态构造，只把每实例两个 setter 改为写入 `PackedFloat32Array`，再对每个非空 MultiMesh 提交一次完整 buffer。场景原本就是 3D transform、无颜色流、有 custom data，因此每实例为 16 个 float32。负 custom alpha 继续编码冲锋步态，没有截断为颜色的常见取值范围。

两套初始容量各 4096 的 CPU 缓冲共 512 KiB；这是新增数组的名义容量，不是进程总内存增量。只存在普通士兵时，每次完整提交 256 KiB；普通与隐身都非空时，共提交 512 KiB，即使可见总人数只有 512 也一样。容量扩至 8192 后上述容量和提交量翻倍。空池不提交 buffer，但仍更新 `visible_instance_count`。

正确性与性能分开运行：无头打包检查 153 项通过；原生 MultiMesh 资源读回检查 261 项通过。覆盖普通／隐身分池、未暴露单位过滤、负 alpha、返程、空中、悬浮、地形校正、4097 人扩容、缩小、清空与再填充，并比较每个可见实例的全部 16 个浮点数和渲染前后的单位状态。

性能采用 512／4096 人、普通／混合隐身，三轮交替 A→B、B→A，预热 30 次、测量 120 次。每次测量包括完整 `_render` 数据构造、打包和提交；另记录姿态更新及两者合计。无头和原生性能运行各 36 项检查通过。

## 候选 B：同步调用边界内合并重复提交，已合入

候选把同一个 `simulate()` 子步循环及房主 `process()` 追赶循环中的多次士兵提交合并到最外层同步调用结束时。内部仍执行全部固定规则步、出兵、命中、死亡、发布与表现事件；只推迟中间的 MultiMesh 提交。批次之外的独立 `send`、`tick`、`hit` 仍立即提交。它与候选 A 的 buffer 打包方案互相独立。

记录 `.local/render-batch/benchmark.json` 包含三轮，每轮 413 项检查全部通过。每个场景预热 4 次、采样 30 次，初始 4096 名士兵；每个样本交换 A/B 先后顺序。夹具准备、断言、快照、事件追踪与资源读回排除在同步操作计时之外。下面的性能表均来自这三轮无头运行。

| 同步操作场景 | 原版：平均 / P95 | B：平均 / P95 | 平均耗时降低 | 30 次样本的提交次数：原版→B |
| --- | ---: | ---: | ---: | ---: |
| 普通单次 `simulate(1/60)` | 25.100 / 26.626 | 25.031 / 26.665 | 约 0.3%，视为持平 | 30→30 |
| `simulate(0.2)` 的多个子步 | 128.017 / 130.197 | 110.757 / 112.767 | 13.5% | 150→30 |
| 密集命中、排队出兵及四步追赶 | 241.603 / 307.361 | 181.464 / 236.096 | 24.9% | 434→30 |
| 房主八个真实固定步追赶 | 290.942 / 334.815 | 260.266 / 305.673 | 10.5% | 240→30 |

这些数值是对应整个同步操作的耗时，其中多步场景刻意一次执行多步，不能直接当作普通显示帧的耗时。密集场景结束时双方都为 4574 名士兵；没有删除士兵来减少负载。八步场景断言每 30 个样本实际执行 240 个规则 tick。

正确性比较覆盖完整规则状态及摘要、有序单位姿态与状态、信号和表现事件的顺序及内容、最终 transform／color／gait 输入、房主发布事实、序号、tick、字节计数和命令结果。边界检查包括零步长、独立 API、嵌套批次、隐身及冲锋、出兵后暂停、暂停中的投降转移、结束时空队列。所有同步 API 返回时批次都已闭合且无待提交状态。

另在原生 Vulkan 运行同一正确性夹具，4096 名士兵，性能循环仅 2 次、无预热，581 项检查通过，记录在 `.local/render-batch/native-summary.log`。该轮检查原生 MultiMesh 资源与最终渲染输入一致，覆盖批次边界；样本数不支持将其作为新的性能表，也不是像素验收。

结论：采用 B；普通单步场景没有可宣称的收益。组合结果另见后文，当前表格不代表组合后的整场加速比例。主要维护风险是新增提前返回或异常路径破坏批次闭合，以及同步信号监听者未来开始依赖中间 MultiMesh 状态；规则与事件仍必须按原顺序执行，不能用跨帧延迟提交替代目前同步边界。

## 候选 C：收窄后的零偏移地形投影 C2，已合入

## 候选 D：跳过零时长范围积分，已合入

候选仅在 `_movement_segment()` 开始处加入 `delta == 0.0` 时返回零的精确分支。原有运动计算按冲锋与普通速度拆分时间段，其中一段为零时仍会进入范围技能处理、查询区间缓存。新分支省略没有时间推进的那一段；不使用近似阈值，不跳过任何正时长区间，不改变冲锋时长、加减速强度或范围边界。

记录 `.local/zero-step-fields/formal/results.json`：三轮，每轮每种候选预热 10 次、采样 120 次，4096 名士兵，六个场景，271506 项检查全部通过，源码前后哈希一致。计时范围是对全军调用 `movement_distance(1/30)` 的固定状态扫描，使用已建立的区间缓存；它不是完整 `present()`、规则 tick 或连续推进的整场测试。

| 固定状态场景 | 原版：平均 / P95 | D：平均 / P95 | 平均耗时变化 |
